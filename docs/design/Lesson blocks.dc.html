How an index decides to be used

An index is not a promise. The planner looks at your query, guesses how many rows come back, and then decides whether reading the index is cheaper than reading the whole table. Today you learn how that guess is made.

Selectivity, in plain words

Selectivity is the share of rows a condition keeps. status = 'refunded' might keep two rows in a million. status = 'paid' might keep nine hundred thousand. Same column, same index, opposite decisions.

The planner does not run your query to find out. It reads statistics that were collected earlier, during ANALYZE: a sample of rows, the most common values in each column, and a histogram of everything else.

From those it estimates a row count. If the estimate is small, an index scan wins: jump to a few places on disk, read a few pages, done. If the estimate is large, the jumps stop being worth it, because each one is a random read and reading the table straight through is sequential.

So when an index is ignored, the useful question is rarely "why is Postgres wrong". It is "what does Postgres think this query returns, and is that number close to the truth".

Default · collapsed

Read the estimate against reality

EXPLAIN ANALYZE
SELECT id FROM orders
WHERE status = 'refunded';

Seq Scan on orders
  rows=1 000 000 → actual rows=2
  time: 412 ms
{{ copyMsgA }}

The estimate is a million rows; the truth is two. The planner is not choosing badly, it is choosing from a bad number.

Run ANALYZE orders; and ask again. With fresh statistics the estimate drops, the index scan becomes the cheaper plan, and the same query returns in under a millisecond.
