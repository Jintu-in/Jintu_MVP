Frames

Day 45 of 91 · 60 min · 35 pts

A window function needs two answers before it can compute anything: which rows are in view, and in what order. The frame is the first answer. Today you set it deliberately instead of taking the default, and you see why the default surprises people.

What a frame is

A partition is the whole group — one customer, one city, one month. A frame is the slice of that group visible from the row being computed right now. It moves with the row.

For a running total, the frame is everything from the start of the partition up to here. For a seven-day moving average, it is the six rows behind plus this one. Same function, same data, different answer — the frame is what changed.

You write it after ORDER BY, inside the OVER clause. If you leave it out, the database picks one for you, and that choice is the subject of most of this lesson.

A running total, written out

SELECT day, revenue,
  SUM(revenue) OVER (
    ORDER BY day
    ROWS BETWEEN UNBOUNDED PRECEDING
             AND CURRENT ROW
  ) AS running_total
FROM daily_sales;

Read the frame line out loud: from the first row of the partition, to this row. That is the whole idea. Everything else on this page is a variation on where those two edges sit.

Two frames evaluated at the same row. The window function sees only the shaded rows.

The frame you get when you write none

Write OVER (ORDER BY day) with no frame and you do not get "no frame". You get RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, which is close to what most people want and not the same thing.

The difference is the word RANGE. It does not count rows. It compares values in the ORDER BY column, so every row holding the same value is inside the frame together, whether you meant it or not.

Gotcha

A moving average written with the default frame is not a moving average. AVG(x) OVER (ORDER BY day) averages everything up to today, so the line looks smooth and drifts less over time — which reads as a real trend and is not one. Write ROWS BETWEEN 6 PRECEDING AND CURRENT ROW and check the first six rows before you trust the chart.

01

Three orders share one date. You want each row to show the total of everything up to and including its own row. ROWS or RANGE?

ROWS. RANGE would give all three the same total, because it groups by the value of the date, not by position. Add a tiebreaker to the ORDER BY as well, or the three rows have no stable order to count in.

A seven-day moving average

SELECT day, revenue,
  AVG(revenue) OVER (
    ORDER BY day
    ROWS BETWEEN 6 PRECEDING
             AND CURRENT ROW
  ) AS avg_7d
FROM daily_sales;
{{ copyMsg }}

The first six rows do not have six rows behind them, so they average two, three, four values and so on. They are not wrong, they are thin — and they will look unusually smooth or unusually spiky at the left edge of any chart.

If that matters, count the rows in the frame with COUNT(*) OVER (same frame) and hide any row where the count is under seven.
02

Your seven-day average starts high on day one and settles by day seven. Is the data wrong?

No. The frame is short at the start of the partition, so those early points average fewer rows. Either hide them or say so on the chart.
Warning

A frame without ORDER BY is legal and almost never what you meant: the whole partition sits in the frame, so every row gets the same number. If your running total is a flat line, check the ORDER BY first.
